# 7. Reasoning-model design

Reasoning specialists should operate over goals, hypotheses, evidence gaps and optional world-model rollouts—not over an undifferentiated transcript.

Candidate specializations:

• decomposition and planning;
• retrieval/search policy;
• debugging and falsification;
• causal hypothesis testing;
• verifier/test generation;
• contradiction resolution;
• compute allocation and stopping.

ReAct supports interleaving reasoning, action and observation rather than separating planning from environment interaction. $^9$ Test-time compute methods include repeated sampling, correction and tree search, but increased compute is not automatically better. $^{10}$ Intrinsic self-correction can degrade reasoning when no external feedback is supplied, supporting independent tests, execution results and fresh evidence as verification signals. $^{11}$

Reasoning experts therefore produce proposals and tests, not authority. A world model is optional: code inspection may require planning and tools but no transition prediction.

8. Expert/procedural models and distillation

Distillation ladder

1. Canonical SKILL.md revision.
2. Executions with route and context proofs.
3. Outcome decomposition: retrieval, selection, execution, tool, answer.
4. Verified positive and negative traces.
5. Stable pattern analysis across project/session/temporal splits.
6. Offline distillation into isolated adapter or small specialist.
7. Shadow comparison against explicit execution.
8. Gated production with fallback.
9. Periodic regression against current skill revision.
10. Disable, retrain or revoke when provenance expires.

Promotion gates

A behavior is mature only if:

• success is objectively verifiable;
• failures and corrections are retained;
• labels agree across independent verifiers;
• performance holds on unseen sessions/projects;
• the skill's constraints survive distillation;
• the expert provides measurable latency/token/quality benefit;
• rollback is tested;
• skill revision, dataset digest and checkpoint are linked.

LoRA freezes base weights and learns low-rank updates, reducing trainable parameters in its evaluated models while preserving competitive task performance. $^{12}$ However, adapter combination is not algebraically safe by default: TIES-Merging documents redundant-update and sign-conflict interference. $^{13}$ MoLE reports similar problems for direct LoRA arithmetic and motivates routed rather than blindly merged adapters. $^{14}$

9. Auditability and reversibility

| Layer | Achievable mechanism | Limit |
| :--- | :--- | :--- |
| Behavioral reversibility | Disable adapter/expert; fall back to skill | Does not explain encoded knowledge |
| Provenance reversibility | Dataset digests, trace IDs, skill revision, code/container/checkpoint hashes | Does not isolate each parameter's meaning |
| Data attribution | Influence estimates, leave-cluster-out tests, TracIn-style analysis | Approximate; expensive; method-dependent |
| Knowledge interpretability | Probes, activation analysis, mechanistic studies | Not comprehensive or solved |
| External assurance | Regression suites, shadow deployment, canaries, observed outcomes | Detects behavior, not internal semantics |

TracIn estimates training-example influence using gradients and saved checkpoints, but influence estimates should be treated as supporting evidence rather than exact provenance. $^{15}$ Mechanistic interpretability still has unresolved conceptual, practical and socio-technical problems, weight-level understanding is not a release gate that current methods can guarantee. $^{16}$

Each expert should ship with a **provenance certificate**: base model, adapter hash, canonical skill revision, trace dataset digest, exclusions, verification policy, evaluation splits, regression results, known failures, allowed activation contexts and rollback target.
